**STATE-04 has now landed: the `SAST-HIST-*` per-finding history boundary refinement, tension 13's second layer composed with STATE-03's first.**
Layer 1 - the (check, cell) coverage test STATE-03 already shipped - is unchanged and still runs first; an uncovered cell is `unknown` without the new layer ever being consulted, exactly as tension 13's own resolution states.
Layer 2 is two new, optional trailing arguments on `findings_classify_absent` (`PRIOR_OLDEST_REACHING_COMMIT_TIME`, `THIS_RUN_OLDEST_COMMIT_TIME`) rather than a second function, so every non-history caller - IaC, SCA, DAST, working-tree SAST - omits both and is byte-for-byte unaffected.
Inside an already-covered cell, for a `SAST-HIST-*` check id only, it compares the absent finding's own `oldest_reaching_commit_time` against this run's resolved `history_boundary.oldest_commit_time` for that check: at or after it, `fixed` stands; before it, `fixed` is downgraded to `unknown\thistory_boundary_receded`.
The boundary is compared as a plain value beside the cell and is never folded into the cell string itself - tension 13's own named trap, which makes two runs with an ordinary, rolling boundary movement describe two different cells and so fail layer 1's coverage test for every prior history finding, permanently.
`tests/suites/state-history-classify.sh` proves this: rows 3-6 of tension 13's own eight-row fixture table (rows 1, 2, 7 and 8 are finding-IDENTITY cases already pinned by `tests/suites/findings.sh` and `tests/suites/sast-history.sh`, and this ticket does not touch identity), a direct proof of the rejected boundary-in-cell reading failing row 6 specifically (the case tension 13 calls "the one that matters most"), and a direction proof that layer 2 can only narrow a layer-1 `fixed` to `unknown`, never promote an `unknown` back to `fixed` - the guards and the uncovered-cell case were re-checked with boundary arguments that would satisfy layer 2 on their own, and stayed `unknown` regardless.
Every new assertion was run against the pre-refinement code and watched fail before the fix landed (rows 3 and 4 specifically), per this project's testing rule.

**STATE-05 has now landed: `classify_derived` wired against tension 12's own guard, closing the one real gap left in an otherwise already-shipped, already-tested mechanism.**
`classify_derived`'s three-condition rule (a)/(b1)/(b2)/(c) was built pure and fixture-tested at step 1, well ahead of STATE-01 through STATE-04, and tension 6's whole nine-row fixture table (cases 1-9) already passed before this ticket - so there was no `classify_derived` behaviour left to invent.
What was missing is that `classify_derived` had no concept of tension 12's GUARD at all: an `fp_schema_mismatch` or `no_prior_state` run made the entire prior state incomparable for every ordinary finding (STATE-03), yet a composite's own contributor-coverage test read straight through `prior_state`/`covered_now` regardless, and its (b1) branch re-implemented (rather than called) the `SAST-HIST-*` boundary comparison STATE-04 built into `findings_classify_absent`, so the two copies could silently diverge.
`classify_derived` now takes GUARD as a new parameter, checked first: `fp_schema_mismatch` and `no_prior_state` short-circuit the whole composite to `unknown` before condition (a) is even consulted, since a composite is not a second, ungoverned path to `fixed` off state the rest of the run has already decided is unusable - `scan_root_id_mismatch` is deliberately NOT handled at this top level, since the composite's own cell is JSON `null`, never `path-root` (tension 12 gates only `path-root` cells).
(b1)'s per-contributor "fixed-eligible" test now literally CALLS `findings_classify_absent` - the same function that would classify that contributor's own ordinary finding - rather than re-testing `_pair_covered` and re-deriving the boundary comparison locally, via a new pure helper (`_derived_contributor_scope`) that maps a contributor's check-id module prefix to its coverage-scope, the identical mapping `lib/records.sh`'s `_records_check_coverage_scope` already enforces at lint time.
This is what makes `scan_root_id_mismatch` protect a `path-root`-scoped contributor (the common case: every worked composite example's SAST/SAST-HIST contributors) exactly as it would protect that contributor's own finding, closing a real lenient-direction gap: before this ticket, a scan-root change whose new tree happened to contain a same-named path made `_pair_covered`'s bare string match report the contributor "covered" and the composite `fixed`, even though the two runs' cells were not honestly comparable at all.
`tests/suites/findings.sh` gains a new section (three cases: `fp_schema_mismatch`, `no_prior_state`, `scan_root_id_mismatch`, the last being this ticket's own acceptance case - a contributor "simply not covered this run") proving each fails under the pre-refactor reading that never consulted GUARD; all nine of tension 6's existing fixture-table cases were re-run unchanged (with `usable` passed explicitly) and still pass, and `tests/suites/gate-mutation-proof.sh`'s condition-(a) mutation proof is updated for the new parameter and still passes.

**STATE-06 has now landed: `lib/diff.sh`, wiring STATE-01 through STATE-05's already-tested classification engine against real state for the first time, plus the report delta this is all for.**
Every prior STATE-0x ticket built and fixture-tested a pure piece of the mechanism but wired it into nothing; this is the ticket where that changes.
`diff_classify_run RUNDIR` is inserted into every module's own `run.sh` (sast, iac, sca, dast) between `derive_findings` (tension 11 stage 4) and its own gate call (stage 7) - the exact stage-5 slot the frozen pipeline reserves for classification - and is safe to call more than once per process, since `scan.sh all` calls it once per module over the same, growing `findings.fields`.
It loads `state/latest.json`, computes tension 12's guard from the real `FP_SCHEMA`/`SCOURSH_SCAN_ROOT_ID` against the loaded prior's own fields, rewrites every present finding's `status` (new/recurring) and - for a recurring one - restores its persisted `first_seen` over today's stamp (tension 11 stage 8's "with their first_seen preserved", which nothing before this ticket implemented: every finding stamped `first_seen` at emission time, unconditionally).
Absent prior findings are classified via `findings_classify_absent` (ordinary) or `classify_derived` (composite, dispatched on whether `contributors` is present) and written to `meta/diff_absent`, a small line-oriented ledger.
**A gap no earlier ticket's own scope covered surfaced here and had to be closed in the same change**: nothing before this ticket ever called `state_add_finding` for a live scan's own findings, so `state_write` (already wired at STATE-02) would have persisted a `findings` array that was permanently empty - coverage would accumulate run over run while nothing was ever `recurring` or `fixed` again. `diff_classify_run` now calls `state_add_finding` for every present finding (guarded by a new `state_write_has_finding` accessor, so a repeated call in one `scan.sh all` run never double-adds and trips `state_add_finding`'s own duplicate-fingerprint `die`).
**A second, independent defect had to be fixed alongside it**: the ledger's first draft separated fields with a tab, and a tab is IFS *whitespace* - `read` folds a run of them into one delimiter and drops an empty field (`reason` is empty for `fixed`; `cell` is empty for a derived finding), silently shifting every later column. Measured directly (a `fixed` row read back as nothing), not assumed; the ledger is 0x1f-separated instead, the same fix `AGENTS.md`'s own "Sharp edges" entry already documents for an unrelated DAST record stream for the identical reason.
`lib/report.sh`'s `report_md`/`report_html` render a new "Since last scan" section leading the report (tension 11 stage 9's own instruction), with the guard's own reason spelled out in prose when it fired, and `Fixed since last scan` / `Not assessed this run` always rendered as two distinct headings - the literal distinction this ticket's own acceptance criterion demands a test prove in text, not only in `run.json`.
The standalone `scan.sh diff --against <prior-run-dir>` command (`diff_render_against`) performs no scan of its own: `--against` names a REPORTS directory, never a `state/` file directly, so its own `state/<run-id>.json` is found by the one thing tying the two together - `SCOURSH_RUN_ID` already defaults to the reports directory's own basename (`lib/core.sh`'s `run_init`) - and "this run" is `state/latest.json` (the most recently completed real scan), never a fresh one.
**One more correctness fix rides along, found while wiring the standalone command**: `scan_main`'s end-of-run `state_write` call was unconditional (STATE-02's own wiring), so a `diff`/`report` invocation - neither dispatches a module, so `_scan_state_begin`'s write-side builder is genuinely empty for them - would persist an empty `state/<run-id>.json` and, worse, overwrite `state/latest.json` with it, corrupting the one reference point every future run's automatic classification depends on. `state_write` is now gated to the six scanning commands (`sast`/`sca`/`iac`/`dast`/`cloud`/`all`) only.
Two of `tests/suites/sast.sh` and `tests/suites/iac.sh`'s own pre-existing `--fail-on-new` gate tests needed an isolated `SCOURSH_INSTALL_ROOT` for the identical reason: run as a bare subprocess against the real repository, they would read and write the real `$ROOT/state/`, and a finding either test's own fixture had already produced in some earlier run would classify `recurring` rather than `new`, silently defeating the gate assertion - the exact regression this ticket's own new classification mechanism makes newly possible, since before it every finding was unconditionally `new`.
`tests/suites/state-diff.sh` is the proof: the four-row table, both guards (including that a `target`-scoped prior finding is unaffected by a `path-root` `scan_root_id` mismatch), the `SAST-HIST-*` boundary refinement, `rule_changed_checks`, the composite rule (reusing the same fixture `tests/fixtures/rules/derived.rules` STATE-03/04/05's own suites already exercise), and the report-text acceptance case, each naming the reading it fails under.

What does NOT exist, in any form: a `state/` directory, a writer or loader for `state/<run-id>.json` / `state/latest.json`, per-(check, cell) coverage recording, the classification engine, `config/baseline.json` handling, or a real `diff` command.
That is the whole of this plan.

## Where step 7 sits in the frozen pipeline

Tension 11's RESOLUTION freezes nine stages and assigns them owners.
Steps 1-4 of the pipeline (collect, fingerprint, merge, derive) shipped at §13 steps 1-3.
**§13 step 7 implements pipeline stages 5 (classify + `diff_usable`), 6 (suppress), and 8 (persist)**, plus the stage-7 gate predicate's `--fail-on-new` carve-out and the stage-9 reporting of deltas, suppressed sections, and stale baseline entries.
The ticket decomposition below is dependency-ordered along that pipeline, which is why it is mostly serial: the pipeline order IS the dependency order, and two tickets editing the same pipeline function in parallel is how merge conflicts (and worse, silent stage reordering) happen.

One consequence of tension 12, restated because every ticket below inherits it: `state/` files are **machine-generated JSON**, not `rules/RULE-FORMAT.md` records - the frozen record format governs human-authored files only, and `state/*.json` sits in the same machine-format family as `findings.jsonl` and `run.json`.
`config/baseline.json` is likewise JSON (tension 11 defines its object schema directly).
No STATE-* ticket touches `rules/RULE-FORMAT.md`, and none may: check ids feed the fingerprint, the format is frozen, and `fp_schema` exists precisely so state can survive the day that ever changes.

## Fixture and test obligations, stated once

Every STATE-* ticket carries its own tests in the same change, per this project's convention - there is no separate test ticket.
Three committed test tables are the floor, not the ceiling: tension 12's eight-row matrix (STATE-03), tension 13's eight-row table (STATE-04), and tension 11's four ordering hazards (STATE-07).
Every test names the reading it fails under, per the `AGENTS.md` testing rule: a test that passes under both the correct and the rejected reading pins nothing.
State fixtures are hand-authored JSON under `tests/fixtures/` (a new `tests/fixtures/state/` subtree is the natural home), never captured from a live run, so the suite stays deterministic and the fixtures stay readable in review.

## Doc-update process

Per `AGENTS.md`'s "Build order and where we are" process rule, whoever lands STATE-01 (the first real step-7 code) updates both `AGENTS.md`'s "Current position" paragraph and `docs/FOUNDATION.md`'s "Where the build currently stands" section in the same change, and runs `tools/gen-status.sh --write` if any generated block is affected.
`docs/DESIGN.md` itself stays verbatim - it is never the place build-order status is recorded.
The same rule applies to whoever lands STATE-08 and thereby completes the step.
